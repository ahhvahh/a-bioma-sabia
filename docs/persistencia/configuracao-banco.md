# Configuração e isolamento do PostgreSQL

![Status](https://img.shields.io/badge/Status-refinement-d4a72c?style=flat-square) ![Versão](https://img.shields.io/badge/Vers%C3%A3o-proposta_v0.1-6e7781?style=flat-square)

## Escolha técnica proposta

- **SGBD:** PostgreSQL relacional.
- **Banco lógico dedicado:** `abioma_sabia`.
- **Schema SQL exclusivo:** `sabia`. Todas as tabelas são identificadas como `sabia.nome_tabela`.
- **Role de runtime:** `sabia`, usuário SQL sem privilégios de DDL.
- **Role proprietária:** `sabia_owner`, sem LOGIN; migrations sob identidade autorizada que assume essa role.
- **Processo Linux:** `sabia` (sem root), no grupo `abioma_db`. `absabia` somente conecta aos UDS da aplicação.
- **Transporte do banco:** UDS PostgreSQL com autenticação SQL local; TCP não pode funcionar como rota alternativa indevida.

Esses **nomes são propostas novas**; o documento original só exige banco lógico e role dedicados. Não assumir que a infraestrutura já esteja configurada.

## Provisionamento inicial ilustrativo

O DBA deve executar operações privilegiadas no banco/cluster adequado:

```sql
-- Executar em sessão administrativa, fora de uma transação.
CREATE ROLE sabia_owner NOLOGIN;
CREATE ROLE sabia LOGIN NOINHERIT;
CREATE DATABASE abioma_sabia OWNER sabia_owner;
REVOKE ALL ON DATABASE abioma_sabia FROM PUBLIC;
GRANT CONNECT ON DATABASE abioma_sabia TO sabia;
```

Na conexão administrativa **ao banco `abioma_sabia`**:

```sql
CREATE SCHEMA sabia AUTHORIZATION sabia_owner;
REVOKE ALL ON SCHEMA sabia FROM PUBLIC;
GRANT USAGE ON SCHEMA sabia TO sabia;
-- Após as migrações (objetos pertencentes a sabia_owner):
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA sabia TO sabia;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA sabia TO sabia;
ALTER DEFAULT PRIVILEGES FOR ROLE sabia_owner IN SCHEMA sabia
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO sabia;
ALTER DEFAULT PRIVILEGES FOR ROLE sabia_owner IN SCHEMA sabia
    GRANT USAGE, SELECT ON SEQUENCES TO sabia;
```

Não executar `CREATE DATABASE` dentro de uma transação. O migrador deve criar os objetos com a role proprietária apropriada; a role `sabia` deve ter DML/uso de sequences, sem `CREATE`, `ALTER`, `DROP` e sem superuser.

## Configuração do acesso por UDS

- No PostgreSQL, definir e validar `unix_socket_directories`, `unix_socket_group` e `unix_socket_permissions` com as políticas do host; são parâmetros **do cluster/instância**, não do banco individual.
- Em `pg_hba.conf`, avaliar uma regra `local abioma_sabia sabia peer` em posição adequada. Como o usuário Linux também será `sabia`, `peer` pode identificar a role SQL sem distribuir senha ao processo.
- Restringir entradas `host` e `listen_addresses` conforme a implantação. Caso o cluster seja compartilhado, avaliar o impacto dessas configurações sobre outros bancos e serviços.
- Proteger diretórios pais e o socket com grupo `abioma_db`; o grupo `absabia` não deve ter permissão no diretório/UDS PostgreSQL.

**Configuração concreta de caminho do socket, cluster, versão do PostgreSQL, backups e credenciais:** pendente de validação no ambiente. Não colocar credenciais ou `raw_update` em logs.

## Contratos de configuração

A seção `database` de `/etc/sabia/sabia.yaml` precisa ser refinada para representar **a conexão por UDS e o banco `abioma_sabia`**. O formato exato da chave YAML ainda não foi aprovado, portanto nenhum exemplo de chave de configuração é normativo.

## Tipos e integridade

| Categoria | PostgreSQL | Convenção |
|---|---|---|
| Identificador da requisição | `uuid` | UUID v4 criado pelo Sabiá |
| PKs geradas | `bigint GENERATED BY DEFAULT AS IDENTITY` | Não confundir com UUID |
| Identidades de bot/chat/usuário | `text` | Preservar valores como identificadores opacos |
| Datas absolutas | `timestamptz` | Instante absoluto, apresentação em UTC |
| Argumentos | `text[]` | Array vazio em vez de NULL quando não houver argumentos |
| Payload Telegram bruto | `jsonb` | Objeto completo, sem tokens |
| Mídias e chunks | `bytea` | Limites de bytes validados |
| Estados | `text` + `CHECK` | Não usar ENUM SQL implícito |
| Booleanos | `boolean` | Não usar strings para `true/false` |

**Índices:** PK/UNIQUE conforme as fichas; criar índices explícitos para FKs e claims de filas, pois a FK por si não cria índice na coluna referenciadora.

**Fontes oficiais:** [CREATE SCHEMA](https://www.postgresql.org/docs/current/sql-createschema.html), [Tipos](https://www.postgresql.org/docs/current/datatype.html), [Restrições e FKs](https://www.postgresql.org/docs/current/ddl-constraints.html), [Conexões por socket](https://www.postgresql.org/docs/current/runtime-config-connection.html) e [pg_hba.conf](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html).
